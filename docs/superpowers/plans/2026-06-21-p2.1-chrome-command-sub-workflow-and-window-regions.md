# P2.1 Chrome Command Sub-Workflow and Window Regions Plan

**Date:** 2026-06-21
**Status:** Current implementation plan
**Scope:** Rename the Chrome command sub-workflow layer, remove the public safety-gate invoke command, make page commands viewport-scoped, add scroll-boundary signaling, clip DOM evidence to the viewport contract, and add browser-chrome domain invoke APIs.

---

## Goal

P2.1 makes CDS Chrome invoke commands region-aware without weakening the self-contained command architecture.

The Chrome window is split into:

- `page_viewport`: the webpage content area, normally represented by Chrome's `AXWebArea`.
- `browser_chrome`: Chrome-owned UI outside the webpage viewport, including toolbar, address bar, tab strip, reload/back/forward controls, extension area, profile button, and settings area.
- `unknown`: evidence that cannot be safely assigned.

Page commands operate only inside `page_viewport`. Browser-chrome operations are exposed as separate Chrome domain invoke APIs.

P2.1 does not introduce persistent page-coverage state, a new `chrome-context` layer, or a new public `OperationResult` contract. It exposes current-invocation scroll-boundary, scroll-progress, post-action observation, and viewport evidence so the caller can decide whether to continue scanning.

---

## Confirmed Decisions

- Keep driver primitives full-window. Do not make screenshot, AXTree, DOM, or OCR primitives viewport-only.
- Build region semantics above primitives in the Chrome command/sub-workflow layer.
- Rename `atomic-commands.ts` to `chrome-command-sub-workflow.ts` first as a mechanical cleanup.
- Delete `chrome.checkSafetyGate` from the public invoke surface.
- Keep `MacOSChromeDriver.checkSafetyGate()` and `safety-gate.ts` as internal driver capabilities.
- Make `chrome.findText`, `chrome.waitForText`, `chrome.clickTarget`, `chrome.typeInput`, and `chrome.scrollRegion` viewport-only.
- Wire `scroll-boundary.ts` into observe, text-miss, and scroll outputs.
- Report current-viewport absence explicitly; do not imply full-page absence from `findText found=false`.
- Clip DOM-derived invoke evidence to the same resolved page viewport used by OCR.
- Keep raw DOM payloads as trace/debug evidence only, not as top-level invoke output.
- Leave `chrome.key` unchanged.
- Add browser-chrome domain invoke APIs for back, forward, reload, and address-bar submit.
- Use Chrome Apple Events / JXA as the primary delivery path for back, forward, and reload after managed-window preflight.
- Add keyboard primitive support for bracket keys before enabling back/forward keyboard fallback.
- Use foreground `Cmd+L` -> text entry -> Return as the primary delivery path for address-bar submit.
- Require profile + window + tab checks for every browser-chrome domain command in the same invocation.
- Use `chrome-window-regions.ts`; do not use `chrome-app-profile.ts` because it conflicts semantically with Chrome user profiles.
- Defer a durable `chrome-context` / `chrome-operation-context` layer.
- Defer AUV-style public `InputActionResult`, `VerificationResult`, and `OperationResult` contracts. P2.1 still returns per-command action outputs such as `scrollRegion` post-observation and scroll-progress data inside the existing invoke result shape.

## Current Public Commands

| Command | P2.1 Status | P2.1 Meaning |
| --- | --- | --- |
| `chrome.observe` | Keep and extend | Observe the Chrome window, optionally scoped to all, viewport, or browser chrome. |
| `chrome.checkSafetyGate` | Remove from public invoke | Internal driver preflight remains. |
| `chrome.findText` | Keep, viewport-only | Find visible webpage text in `page_viewport`. |
| `chrome.waitForText` | Keep, viewport-only | OCR-poll for webpage text in `page_viewport`; final enrichment only. |
| `chrome.clickTarget` | Keep, viewport-only | Click webpage targets inside `page_viewport`. |
| `chrome.typeInput` | Keep, viewport-only | Replace text in webpage input targets inside `page_viewport`. |
| `chrome.key` | Keep unchanged | Send a key event to the active Chrome window/control. |
| `chrome.scrollRegion` | Keep, viewport-relative | Scroll inside a normalized rectangle relative to `page_viewport`. |

New browser-chrome domain commands:

| Command | Meaning |
| --- | --- |
| `chrome.back` | Go back in the active tab of the leased managed Chrome window using Apple Events primary delivery, with foreground keyboard fallback. |
| `chrome.forward` | Go forward in the active tab of the leased managed Chrome window using Apple Events primary delivery, with foreground keyboard fallback. |
| `chrome.reload` | Reload the active tab of the leased managed Chrome window using Apple Events primary delivery, with foreground keyboard fallback. |
| `chrome.addressBarSubmit` | Focus the omnibox with foreground `Cmd+L`, type text, and submit with Return. |

## Architecture Model

CDS should be understood as a matrix.

Horizontal layers:

1. CLI flat flags
2. invoke catalog
3. invoke runtime
4. invoke handlers
5. `MacOSChromeDriver`
6. Chrome command sub-workflow
7. primitive capabilities: screenshot, AXTree, Chrome DOM, OCR, pointer, keyboard, scroll

Vertical command chains:

- `observe`: CLI -> catalog/runtime -> handler -> driver observation -> region-scoped observation assembly
- `findText`: CLI -> catalog/runtime -> handler -> driver operation -> command sub-workflow -> viewport OCR/AX/DOM recognition -> current-viewport absence/scroll known limits
- `clickTarget`: CLI -> catalog/runtime -> handler -> driver operation -> command sub-workflow -> viewport target resolution -> foreground click
- `scrollRegion`: CLI -> catalog/runtime -> handler -> driver operation -> command sub-workflow -> before scroll boundary -> viewport scroll delivery -> after scroll boundary/progress evidence
- `chrome.back`: CLI -> catalog/runtime -> handler -> browser-chrome domain operation -> managed lease preflight -> Apple Events selected-window active-tab command -> active-tab metadata check/fallback

Do not introduce a second hidden executor, recipe runner, cross-invoke state store, or generic app-local workflow layer.

## Phase 2: Chrome Window Regions

Purpose: create a shared region model for the resolved Chrome window.

Create:

- `src/computer-use/macos-chrome-driver/chrome-window-regions.ts`

Region types:

```ts
export type ChromeWindowRegion
  = | 'page_viewport'
    | 'browser_chrome'
    | 'unknown'
```

Scope types:

```ts
export type ChromeObservationScope = 'all' | 'viewport' | 'browser_chrome'
```

Core output:

```ts
export interface ChromeWindowRegionMap {
  windowBounds: Bounds
  pageViewport?: {
    bounds: Bounds
    confidence: 'verified'
    source: 'ax_web_area'
    reasons: string[]
  }
  regions: Array<{
    region: ChromeWindowRegion
    bounds: Bounds
    confidence: 'verified' | 'inferred' | 'fallback' | 'unknown'
    source: 'ax_structure' | 'geometry' | 'mixed' | 'fallback'
    reasons: string[]
  }>
  knownLimits: string[]
}
```

Rules:

- `page_viewport` is verified only from valid `AXWebArea` evidence.
- `browser_chrome` is the P2.1 coarse label for Chrome-owned UI outside the webpage viewport.
- Do not silently set `page_viewport = window.bounds`.
- If no viewport is found, page commands must not fall back to whole-window targeting.
- Browser-chrome evidence must stay visible in `observe`, but page commands must not target it.
- Region confidence is categorical plus reasons, not a numeric score.
- `AXWebArea.bounds` is the only verified page viewport source.
- OCR and DOM evidence are viewport evidence only when produced inside or clipped to the resolved `AXWebArea` bounds.
- Whole-window, cross-region, or ancestor AX nodes must not be tagged `page_viewport` solely because their center point falls inside the viewport.
- AX traversal is used to find the resolved Chrome window and its `AXWebArea`; arbitrary AX parent nodes are not promoted into viewport targets.
- Do not expose fine-grained browser-chrome subregion tags in P2.1. `chrome_address_bar`, `chrome_toolbar`, `chrome_tab_strip`, `chrome_menu_bar`, and `chrome_bookmarks_bar` require source-verified AX role/bounds rules before they become public region values.

Verification:

- AXWebArea-derived viewport is classified.
- Missing AXWebArea produces known limits and no fake page viewport.
- AX nodes outside AXWebArea are classified as browser chrome or unknown.
- Whole-window or cross-region AX parent nodes are not classified as viewport nodes.
- OCR/row boxes are classified using the same window region map.

## Phase 3: Region-Scoped Observation

Purpose: let `chrome.observe` return a merged observation for all, viewport-only, or browser-chrome-only scopes.

Design:

- Driver primitives still capture the full Chrome window.
- Observation assembly builds one `ChromeWindowRegionMap`.
- `normalizeToSurfaceNodes()` or its caller attaches region metadata to each `SurfaceNode`.
- The handler accepts an optional scope input.

Candidate input name:

- `scope=all|viewport|browser_chrome`

Default:

- `all`

Scope semantics:

- `all` includes `page_viewport`, `browser_chrome`, and `unknown`.
- `viewport` includes only `page_viewport`.
- `browser_chrome` includes evidence tagged `browser_chrome`.
- `unknown` is excluded from scoped outputs unless a later diagnostic mode is explicitly designed.

Output requirements:

- Every node has region metadata when classification is available.
- `detail` includes region known limits when classification is incomplete.
- Observation `known_limits` includes region-map known limits.
- Observation `detail` includes current scroll-boundary metrics when available.
- Observation `known_limits` explains when scroll-boundary metrics are unavailable.

Verification:

- `chrome.observe` default includes page and browser-chrome evidence.
- `chrome.observe --scope viewport` returns page nodes only.
- `chrome.observe --scope browser_chrome` returns browser-chrome nodes only.
- `chrome.observe` reports current `canScrollDown`, `canScrollUp`, `atTop`, and `atBottom` when metrics are available.
- Browser chrome is not deleted silently.

## Phase 4: Viewport-Only Page Commands

Purpose: make page commands unable to accidentally target browser chrome.

Commands:

- `chrome.findText`
- `chrome.waitForText`
- `chrome.clickTarget`
- `chrome.typeInput`
- `chrome.scrollRegion`

Rules:

- `findText` OCR runs with viewport crop.
- `findText found=false` means no current-viewport match. It must not claim full-page absence.
- `findText found=false` includes known limits such as `text_not_found_in_current_viewport` and, when scroll state allows, `text_may_be_below_viewport`.
- `waitForText` resolves verified viewport geometry once at invocation start, then polls OCR-only against that viewport crop.
- `waitForText` final enrichment uses the same viewport region map.
- `clickTarget` candidates are built only from viewport evidence.
- `typeInput` candidates are input-capable viewport targets only.
- `typeInput` must not gain an address-bar mode and must not accept browser-chrome targets.
- `hint` remains a spatial disambiguation input inside the viewport candidate set; it is not combined with semantic browser-chrome regions.
- `scrollRegion` normalized ratios are relative to `page_viewport`, not the full window.
- `scrollRegion` must deliver scroll input at a computed point inside the viewport. It must not default to a pre-click because click events can change page state.
- `scrollRegion` captures scroll-boundary state before and after delivery when possible.
- `scrollRegion` reports whether scroll metrics or visible content changed.
- `scrollRegion` reports boundary/no-progress known limits when the scroll step cannot prove progress.
- `scrollRegion` performs a post-scroll observation after delivery and returns that observation context directly; callers must not need a separate `chrome.observe` just to learn whether the scroll worked.
- DOM-derived invoke evidence is clipped to the resolved page viewport. Raw DOM stays as trace/debug evidence, not top-level invoke output.
- DOM viewport and document metrics are retained as normalized metadata for geometry projection, matching audit, and scroll-boundary; removing raw DOM from public output must not discard these metrics.

Region timing:

- `findText`, `clickTarget`, and `typeInput` use region metadata after enrichment.
- `waitForText` may capture AX once before polling to resolve verified viewport bounds.
- `waitForText` polling does not build a full region map or capture AX/DOM on each poll.
- `waitForText` polling uses only the resolved viewport OCR crop; final enrichment adds region metadata.
- `scrollRegion` uses viewport geometry directly.

Failure behavior:

- If no verified page viewport exists, page commands return a clear failure/refusal instead of falling back to the full window.
- If OCR crop cannot be calculated, text commands report the missing viewport as a known limit.

Verification:

- Toolbar/address-bar text is not found by `findText`.
- `findText found=false` includes current-viewport absence semantics and scroll-related known limits.
- Toolbar/address-bar text is not clicked by `clickTarget`.
- Page input targeting does not target address bar or browser chrome search fields.
- `typeInput` has no address-bar mode.
- `scrollRegion` computes global scroll coordinates from viewport-relative ratios and does not perform a default pre-click.
- `scrollRegion` returns before/after scroll-boundary state when available.
- `scrollRegion` can report no-progress or boundary-reached without claiming semantic task success.
- `waitForText` still does not capture AX/DOM on every poll.
- `waitForText` region metadata appears only on the final enriched result.
- DOM output visible to invoke callers is normalized and viewport-clipped.

## Phase 4.5: Scroll Boundary Wiring

Purpose: make current viewport coverage visible without introducing hidden cross-invoke state.

Use existing:

- `src/computer-use/macos-chrome-driver/scroll-boundary.ts`
- AX scroll evidence already emitted by `captureAXTree()` for real scroll controls. `AXWebArea.AXValue` is accessible value text, not page scroll position, and must not be consumed as scroll state.
- DOM viewport metrics already captured in the Chrome DOM observer before conversion.

Design correction:

- `scroll-boundary.ts`, DOM viewport metrics, valid AX scrollbar evidence, and post-scroll deltas are one scroll-boundary capability.
- Chrome webpage scroll-boundary is DOM-metrics-primary in P2.1. AX evidence may corroborate only when a real `AXScrollBar` exposes numeric value/min/max evidence. `AXWebArea` and incomplete AX scroll evidence must produce known limits, not `ax_scroll_value` basis.
- When an AX snapshot exists but no usable Chrome page scrollbar evidence is exposed, report `macos_ax_bridge_does_not_expose_chrome_page_scroll_offsets`; this is a known bridge limitation, not a transient capture failure.
- DOM viewport/document metrics must not be dropped while converting raw DOM into `ChromeDomObservation`; they are required for scroll-boundary and geometry audit.

Wire into:

- `MacOSChromeDriver.observe()`
- `chrome.findText`
- `chrome.waitForText` final result only
- `chrome.scrollRegion`
- trace visual report

Required data:

- AX scroll evidence:
  - scroll-bearing role: `AXScrollBar` only for page-boundary basis in P2.1
  - orientation
  - numeric current value
  - numeric min/max value
  - bounds
  - relation to resolved `AXWebArea`
- DOM viewport/document metrics:
  - viewport width/height
  - scroll X/Y
  - document scroll width/height
  - document client width/height
  - known limits when Apple Events JavaScript execution is unavailable
- vertical scroll offset when available
- viewport height
- scroll height
- `canScrollUp`
- `canScrollDown`
- `atTop`
- `atBottom`
- evidence basis: DOM metrics, valid AX scrollbar value, post-scroll delta, screenshot diff, or unknown
- known limits when metrics are unavailable or heuristic

Rules:

- Do not mutate page state inside `observe` to discover boundaries.
- Do not persist page coverage in the driver or invoke layer.
- Do not infer full-page absence from one viewport.
- Do not auto-scroll inside `findText`.
- Do not treat `AXWebArea.AXValue`, `AXMinValue`, `AXMaxValue`, `AXVisibleCharacterRange`, or `AXNumberOfCharacters` as Chrome page scroll state. Current Chrome macOS AX bridge may expose those attributes without useful page scroll offsets.
- `findText` uses its existing AX/DOM enrichment path to compute scroll-boundary data for current-viewport misses.
- `scrollRegion` captures before boundary state, delivers foreground scroll, then performs a post-scroll observation with AX, DOM-derived normalized metrics, OCR/visible evidence when available, region map, artifacts, and known limits.
- `scrollRegion` compares before/after metrics or visible content to report progress/no-progress.
- A future explicit scan command may maintain same-invocation coverage state. That is outside P2.1; P2.1 does not perform AUV-style multi-scroll page scanning.

Verification:

- `observe` returns scroll-boundary metadata when DOM metrics or valid AX scrollbar metrics are available.
- AXWebArea string/incomplete evidence does not contribute `ax_scroll_value` basis and instead reports `macos_ax_bridge_does_not_expose_chrome_page_scroll_offsets` when an AX snapshot was captured.
- Valid AX scrollbar evidence contributes to scroll-boundary results instead of remaining unconsumed trace data.
- DOM viewport/document metrics survive DOM normalization and contribute to geometry audit and scroll-boundary.
- `findText found=false` reports current-viewport absence and whether more content may exist.
- `scrollRegion` reports before/after boundary state, post-scroll observation context, and no-progress evidence.
- No code stores hidden cross-invoke page coverage.

## Phase 5: Browser-Chrome Domain Invoke APIs

Purpose: expose fixed Chrome UI actions without abusing page commands.

Commands:

- `chrome.back`
- `chrome.forward`
- `chrome.reload`
- `chrome.addressBarSubmit`

Catalog grouping:

- Command ids are `chrome.back`, `chrome.forward`, `chrome.reload`, and `chrome.addressBarSubmit`.
- Catalog metadata should identify these as browser-chrome/domain actions, separate from page viewport actions.

Implementation rules:

- Do not implement these as wrappers around `chrome.clickTarget` or `chrome.typeInput`.
- Run the same-invocation profile + window + tab preflight before delivery:
  - profile lease matches the configured managed profile.
  - leased OS window is found by `windowNumber`, `ownerPid`, and bundle.
  - leased window is raised if needed.
  - leased window is verified foreground before delivery.
  - active-tab metadata is read from the selected Chrome window before and after delivery when available.
- Use Chrome Apple Events / JXA as the primary delivery path for `chrome.back`, `chrome.forward`, and `chrome.reload`.
- Apple Events must bind to the leased Chrome window. Do not blindly use `window 1`.
- Resolve the Apple Events window object from same-invocation leased OS-window evidence such as bounds, title, active-tab metadata, and foreground verification.
- Refuse or fall back when the Apple Events window selector cannot uniquely match the leased window.
- Do not directly reuse first-match helpers such as the current DOM/foreground JXA selectors unless they are hardened to count matches and emit uniqueness evidence.
- Add or harden a dedicated Chrome Apple Events/JXA helper that lists Chrome windows and returns bounds, Apple Events window index/id when available, active tab index, tab id when available, active tab URL/title/loading, and candidate count.
- Use foreground keyboard as fallback for `chrome.back`, `chrome.forward`, and `chrome.reload`; P2.1 fallback uses `Cmd+[`, `Cmd+]`, and `Cmd+R`.
- Add bracket key mapping to the keyboard primitive before enabling back/forward keyboard fallback. If bracket mapping is unavailable, report back/forward keyboard fallback as unavailable instead of attempting `Cmd+Left` or `Cmd+Right`.
- Use foreground keyboard as the primary delivery path for `chrome.addressBarSubmit`.
- Keep `chrome.key` unchanged.
- Do not use AXPress, AX focus write, AX set value, CDP, Playwright, WebDriver, or `open_url`.
- AXTree may provide observation, diagnostics, or fallback evidence, but it is not the primary target discovery path for these four commands.

`chrome.back`, `chrome.forward`, `chrome.reload`:

- Resolve the managed Chrome lease and foreground preflight.
- Resolve the matching Apple Events window object from the leased OS window evidence.
- Read active-tab identity from that same bound Apple Events window before delivery: active tab index, tab id if exposed, URL, title, and loading state when available.
- Execute the corresponding command against `active tab` of that selected Apple Events window:
  - `go back`
  - `go forward`
  - `reload`
- Read after-delivery active-tab metadata from the same bound window when available.
- Treat unavailable history entry or unchanged URL as semantic no-op/known limit, not automatically as delivery failure.
- Fallback to foreground keyboard only after leased-window foreground verification.

`chrome.addressBarSubmit`:

- Input: `text`.
- Resolve the managed Chrome lease and foreground preflight.
- Read before active-tab metadata from the leased window when available.
- Press `Cmd+L` to focus the omnibox.
- Type the submitted text with lower-level foreground text primitive.
- Press Return.
- Read after active-tab metadata from the leased window when available.
- Do not call the page `typeInput` target resolver.
- Do not default to Apple Events `set URL`; that bypasses omnibox search/history/autocomplete semantics.
- Reuse lower-level foreground keyboard/type primitives only.
- Emit known limits for omnibox autocomplete/history/navigation behavior.

Output requirements:

- foreground preflight result
- delivery path
- Apple Events selected-window evidence when used, including why it was considered unique
- keyboard fallback evidence when used
- before/after active-tab metadata when available, read from the same bound Chrome window
- artifacts
- known limits

Verification:

- Catalog resolves all browser-chrome commands.
- Handlers validate inputs.
- Commands do not reuse page command target resolution.
- Commands do not require a preceding `chrome.observe` invocation.
- `back`, `forward`, and `reload` use Apple Events primary delivery.
- Apple Events delivery refuses or falls back when selected-window binding is missing or ambiguous.
- Apple Events selected-window binding reports candidate count or equivalent uniqueness evidence.
- Keyboard fallback requires leased-window foreground verification and uses `Cmd+[`, `Cmd+]`, and `Cmd+R`.
- Address bar submit uses foreground `Cmd+L`, text entry, and Return.
- Address bar submit reports text length, not full sensitive value.
- Address bar submit does not call the page `typeInput` target resolver.
- Address bar submit records before/after active-tab metadata when available.
- Keyboard primitive supports bracket keys or back/forward keyboard fallback reports unavailable.

- No public candidate consumer in P2.1.
- No direct AX action delivery path.
- No JSON recipe runner.
- No fixed browser workflow script.
- No hidden fallback from page viewport to full Chrome window.
- No persistent driver-level or invoke-level page coverage memory.
