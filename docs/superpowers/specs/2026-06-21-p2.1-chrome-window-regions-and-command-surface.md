# P2.1 Chrome Window Regions and Command Surface — Design Spec

**Status:** Current architecture spec
**Date:** 2026-06-21
**Scope:** Chrome command sub-workflow cleanup, Chrome window region modeling, viewport-scoped page commands, scroll-boundary signaling, DOM viewport clipping, and browser-chrome domain invoke APIs.

---

## Positioning

P2.1 is a Chrome-window command-surface correction. It keeps the self-contained command design from P2, but fixes the fact that current observation and command targeting mix webpage viewport evidence with Chrome-owned UI such as the toolbar, address bar, tabs, profile button, extensions, and settings controls.

The term "viewport" means the webpage content area inside Chrome, normally represented by the Chrome AXTree `AXWebArea`. Browser chrome means Chrome-owned UI outside that webpage viewport.

This spec deliberately avoids the name "Chrome App Profile". In Chrome terminology, "profile" already means a browser user profile. P2.1 uses `chrome-window-regions.ts` to model areas of a single resolved Chrome window.

P2.1 deliberately does not introduce a persistent `chrome-context` layer, an AUV-style multi-scroll scan workflow, or a new public `OperationResult` contract. Those remain follow-on design work. P2.1 instead returns explicit per-invocation scroll-boundary, scroll-progress, post-action observation, and viewport evidence so the caller can decide whether to continue exploring the page.

---

## Goals

1. Rename the current Chrome command orchestration entrypoint from `atomic-commands.ts` to `chrome-command-sub-workflow.ts`.
2. Remove `chrome.checkSafetyGate` from the public invoke surface while preserving the driver-level safety-gate API.
3. Keep low-level Chrome primitives full-window.
4. Add `chrome-window-regions.ts` to classify visible evidence into webpage viewport, browser chrome, and unknown regions.
5. Make page commands operate only inside `page_viewport`.
6. Wire scroll-boundary and scroll-progress signals into observation, text search, and scroll commands.
7. Clip DOM-derived evidence to the same page viewport contract used by OCR and do not expose raw DOM as a top-level invoke result.
8. Add separate browser-chrome domain invoke APIs for back, forward, reload, and address-bar submit.
9. Preserve managed Chrome safety: commands still act only inside the leased managed Chrome window.

---

## Current Baseline

Already present:

- `profile.json` loaded by `loadProfileConfig()`.
- managed Chrome bootstrap and lease validation in `MacOSChromeDriver`.
- `MacOSChromeDriver.checkSafetyGate()` and `safety-gate.ts`.
- `--target managed` CLI support.
- full-window capture, OCR, OCR row grouping, AX capture, and atomic commands.
- trace evidence for screenshots, capture contracts, OCR reports, AX reports, and action results.

Missing:

- semantic region tags on observed nodes.
- a shared Chrome window region model.
- scroll-boundary and scroll-progress signals in current command outputs.
- reliable absence semantics for viewport-only text misses.
- DOM evidence clipping to the same viewport contract as OCR.
- viewport-only matching for page commands.
- browser-chrome domain commands that do not reuse page command target resolution.
- command output that explains when evidence came from browser chrome versus page viewport.

## Public Invoke Surface

P2.1 changes the public command surface.

Keep and update:

- `chrome.observe`
- `chrome.findText`
- `chrome.waitForText`
- `chrome.clickTarget`
- `chrome.typeInput`
- `chrome.key`
- `chrome.scrollRegion`

Remove from public invoke:

- `chrome.checkSafetyGate`

Add browser-chrome domain commands:

- `chrome.back`
- `chrome.forward`
- `chrome.reload`
- `chrome.addressBarSubmit`

`chrome.checkSafetyGate` remains a driver-level internal API. Page actions and browser-chrome domain commands must perform their own preflight checks inside the same invocation that performs the action.

## Region Model

Define a semantic region type:

```ts
export type ChromeWindowRegion
  = | 'page_viewport'
    | 'browser_chrome'
    | 'unknown'
```

Rules:

- `page_viewport` is the page content area where normal website actions should default.
- `browser_chrome` is the P2.1 coarse region for all Chrome-owned UI outside the webpage viewport.
- `unknown` means the region classifier could not classify the evidence safely.
- Region tags are metadata. They must not delete evidence.
- `page_viewport` must not be inferred by silently falling back to full-window bounds.
- Browser chrome evidence may be observed, but page commands must not target it.
- P2.1 does not expose finer browser-chrome subregions such as address bar, toolbar, tab strip, menu bar, or bookmarks bar because their Chrome AX role/bounds rules have not been source-verified yet.

## Chrome Window Regions Module

Create `src/computer-use/macos-chrome-driver/chrome-window-regions.ts`.

Responsibilities:

- derive webpage viewport bounds from AX evidence when available.
- derive `page_viewport` from the resolved Chrome window's `AXWebArea`.
- classify OCR match and OCR row bounds by intersecting them with the resolved `AXWebArea` viewport.
- classify browser-chrome evidence as outside the resolved `AXWebArea` and inside the resolved Chrome window.
- expose known limits when region geometry is incomplete.
- avoid fixed global pixel constants such as "top 96 px is browser chrome" as verified region facts.
- avoid assigning `page_viewport` to whole-window or cross-region parent nodes merely because their center point falls inside the viewport.

Required public functions:

```ts
export type ChromeObservationScope = 'all' | 'viewport' | 'browser_chrome'

export interface ChromeWindowRegionMap {
  windowBounds: { x: number, y: number, width: number, height: number }
  pageViewport?: {
    bounds: { x: number, y: number, width: number, height: number }
    confidence: 'verified'
    source: 'ax_web_area'
    reasons: string[]
  }
  regions: Array<{
    region: ChromeWindowRegion
    bounds: { x: number, y: number, width: number, height: number }
    confidence: 'verified' | 'inferred' | 'fallback' | 'unknown'
    source: 'ax_structure' | 'geometry' | 'mixed' | 'fallback'
    reasons: string[]
  }>
  knownLimits: string[]
}

export function buildChromeWindowRegionMap(input: {
  windowBounds: { x: number, y: number, width: number, height: number }
  axRoot?: AXNode
}): ChromeWindowRegionMap

export function classifyChromeWindowRegion(input: {
  regionMap: ChromeWindowRegionMap
  box: { x: number, y: number, width: number, height: number }
}): {
  region: ChromeWindowRegion
  confidence: 'verified' | 'inferred' | 'fallback' | 'unknown'
  source: 'ax_structure' | 'geometry' | 'mixed' | 'fallback'
  reasons: string[]
}
```

Classification rules:

- `AXWebArea.bounds` is the only verified `page_viewport` source in P2.1.
- OCR boxes and DOM boxes are `page_viewport` only when they are produced inside the resolved viewport crop or safely intersect the `AXWebArea` bounds.
- Browser-chrome evidence is inside the resolved Chrome window and outside the resolved `AXWebArea`.
- Whole-window, cross-region, or ancestor AX nodes must not be tagged as `page_viewport` solely by center-point geometry. They must be dropped from scoped viewport output or tagged `unknown` with `region_source: "mixed"` and known limits.
- AX subtree traversal may be used to find the resolved window and `AXWebArea`; it must not be used to promote arbitrary ancestor nodes into viewport targets.

Fallback behavior:

- If AX structural evidence cannot identify a page viewport, classify safely as `unknown` or `browser_chrome`.
- Conservative fallback labels are allowed for non-page evidence only when they are explicitly marked `confidence: 'inferred'`, `source: 'fallback'`, and accompanied by known limits.
- Do not silently claim `page_viewport` from a hardcoded top inset or expose fallback geometry as a verified AX-derived viewport.

## Observation Integration

`chrome.observe` must include region tags on relevant evidence nodes:

- AX nodes.
- OCR text nodes.
- OCR row evidence when rows are surfaced.
- action-relevant merged nodes.

Each tagged item must expose:

```json
{
  "region": "page_viewport",
  "region_confidence": "verified",
  "region_source": "ax_structure",
  "region_reasons": ["AXWebArea intersected the resolved Chrome window"]
}
```

If classification is incomplete:

- keep the node.
- set `region: "unknown"` or `region: "browser_chrome"`.
- include `known_limits`.

Observation accepts an optional scope:

```bash
cds invoke chrome.observe --scope all
cds invoke chrome.observe --scope viewport
cds invoke chrome.observe --scope browser_chrome
```

Default scope is `all`.

Scope filtering rules:

- `all` returns all retained evidence, including `page_viewport`, `browser_chrome`, and `unknown`.
- `viewport` returns only evidence tagged `page_viewport`.
- `browser_chrome` returns evidence tagged `browser_chrome`.
- `unknown` evidence is included only in `all` unless a later command explicitly defines a diagnostic mode.

Scroll-boundary output:

- `chrome.observe` must report current page scroll metrics when DOM metrics or valid AX scrollbar evidence can provide them.
- Scroll-boundary, DOM viewport metrics, valid AX scrollbar evidence, and post-scroll deltas are one capability. `AXWebArea.AXValue` is accessible value text, not page scroll position, and must never feed `ax_scroll_value` basis.
- DOM viewport/document metrics are the primary Chrome webpage scroll-boundary source in P2.1. They must be preserved as normalized metrics, not discarded during DOM observation conversion.
- The output must include whether the page can scroll up/down, whether the current viewport is at the top/bottom, and known limits when metrics are unavailable.
- `observe` must not mutate page state to discover boundaries.
- `observe --scope viewport` still reports scroll-boundary metadata for the current page viewport even though browser-chrome evidence is filtered from nodes.

Scroll-boundary source priority:

1. DOM viewport/document metrics from the selected active tab.
2. Valid AX `AXScrollBar` evidence with numeric value/min/max, when Chrome exposes a real scrollbar node.
3. Post-scroll before/after deltas from `scrollRegion`.
4. Visual/OCR diff when structured metrics are unavailable.

Each scroll-boundary result must report the basis it used. If AX and DOM disagree, the result must expose the conflict in known limits rather than silently choosing one source.

AX evidence rules:

- `AXWebArea`, `AXScrollArea`, `AXVisibleCharacterRange`, and `AXNumberOfCharacters` are not Chrome page scroll offset sources in P2.1.
- Incomplete AX evidence, string `AXValue`, missing numeric min/max, or non-scrollbar roles must report known limits. When an AX snapshot exists but Chrome page scroll offsets are not exposed through usable scrollbar evidence, report `macos_ax_bridge_does_not_expose_chrome_page_scroll_offsets`.
- `ax_scroll_value` basis is allowed only for real `AXScrollBar` evidence with numeric value, min, and max.

The scroll-boundary shape is:

```ts
export interface ChromeScrollBoundary {
  api_version: 'careerdeepseek.scroll_boundary.v1alpha1'
  axis: 'vertical'
  scrollTop?: number
  scrollHeight?: number
  viewportHeight?: number
  viewportWidth?: number
  scrollLeft?: number
  scrollWidth?: number
  canScrollUp: boolean | 'unknown'
  canScrollDown: boolean | 'unknown'
  atTop: boolean | 'unknown'
  atBottom: boolean | 'unknown'
  basis: Array<'dom_scroll_metrics' | 'ax_scroll_value' | 'post_scroll_delta' | 'screenshot_diff' | 'unknown'>
  confidence: 'verified' | 'heuristic' | 'unknown'
  knownLimits: string[]
}
```

## Page Command Semantics

Page commands are viewport-only:

- `chrome.findText`
- `chrome.waitForText`
- `chrome.clickTarget`
- `chrome.typeInput`
- `chrome.scrollRegion`

Rules:

- `findText` runs OCR against the webpage viewport, not the full Chrome window.
- `findText found=false` means the query was not found in the current page viewport. It must not imply full-page absence.
- When `findText found=false` and scroll metrics indicate more content may exist, the result must include known limits such as `text_not_found_in_current_viewport` and `text_may_be_below_viewport`.
- `waitForText` first resolves verified viewport geometry once at invocation start, then keeps polling OCR-only against that viewport crop; AX/DOM enrichment still happens only on the final result.
- `clickTarget` resolves targets only from viewport evidence.
- `typeInput` resolves input targets only from viewport evidence.
- `typeInput` must not accept browser-chrome regions, focus the address bar, or serve as the address-bar input path.
- `typeInput` remains a webpage input command: find a viewport input target, foreground-click it, replace the current value, and optionally submit.
- `scrollRegion` ratios are relative to `page_viewport`, not the full Chrome window.
- `scrollRegion` must deliver scroll input at a computed point inside the viewport. It must not perform a default pre-click because a click can trigger page events unrelated to scrolling.
- `scrollRegion` must capture scroll-boundary state before and after delivery when possible.
- After delivery, `scrollRegion` must immediately perform a post-scroll observation. The caller must not need to issue a separate `chrome.observe` to learn whether scrolling changed the page.
- The post-scroll observation must include the same relevant context as ordinary viewport observation: resolved page viewport, region map, AX evidence, DOM-derived normalized metrics, OCR/visible evidence when available, scroll-boundary state, artifacts, and known limits.
- `scrollRegion` must report whether scroll delivery changed scroll metrics or visible content, whether a boundary was reached, and known limits when no progress can be proven.
- If no verified page viewport exists, page commands must not fall back to full-window targeting.

`hint` remains a spatial disambiguation input for page commands. In P2.1, it is applied only after the page command has already restricted candidates to `page_viewport`. Browser-chrome disambiguation is not expressed as `region + hint` on page commands; browser-chrome commands own their domain-specific delivery path.

Region injection timing:

- `observe` attaches region metadata during observation assembly.
- `findText`, `clickTarget`, and `typeInput` attach and consume region metadata after enrichment.
- `waitForText` may capture AX once before polling to resolve verified viewport bounds. It must not capture AX/DOM inside each poll. The polling loop only uses the resolved viewport OCR crop; region metadata is attached during final enrichment.
- `scrollRegion` uses the viewport geometry directly rather than matching region-tagged nodes.

Scroll completion semantics:

- P2.1 does not persist page coverage across invocations.
- P2.1 does not claim full-page absence from a single `findText` or `observe`.
- A caller can infer "keep scrolling" only from explicit current-invocation signals such as `canScrollDown`, `atBottom`, and `text_may_be_below_viewport`.
- A caller can infer "this scroll step made no progress" from `scrollRegion` before/after metrics or visible-content delta.
- A future scan command may maintain same-invocation page coverage state, but that is outside this P2.1 spec.
- P2.1 does not perform AUV-style `observe -> scroll -> observe` loops inside a single page scan command. `scrollRegion` is a single-step command with action output and post-observation.

DOM evidence:

- Raw DOM observations are internal trace/debug artifacts, not top-level invoke API output.
- DOM evidence returned through invoke must be normalized into `SurfaceNode`, cross-source audit summaries, viewport geometry metadata, or scroll metrics.
- Dropping raw DOM from the public invoke output must not drop DOM viewport metrics. The normalized DOM metrics required for geometry projection and scroll-boundary include viewport width/height, scroll X/Y, document scroll width/height, document client width/height, and known limits.
- DOM text and DOM element labels must be clipped to the resolved page viewport. Container `innerText` that includes text outside the current viewport must not be exposed as visible viewport text.
- DOM elements that are only useful for cross-source audit may remain in trace artifacts but should not become targetable viewport nodes unless their visible bounds and visible text are inside the viewport.

## Browser-Chrome Domain Commands

Browser-chrome actions are separate invoke APIs. They must not be implemented as wrappers around `chrome.clickTarget` or `chrome.typeInput`.

Commands:

- `chrome.back`
- `chrome.forward`
- `chrome.reload`
- `chrome.addressBarSubmit`

Source-backed native Chrome facts:

- Chrome Apple Events expose windows, `active tab`, `active tab index`, tab `URL`, tab `title`, tab `loading`, and tab commands `go back`, `go forward`, and `reload`.
- Chrome Apple Events do not expose Chrome profile directory/path as a structured field.
- CDS already has a managed profile/window lease that validates profile configuration, resolves a Chrome OS window, and verifies foreground ownership through driver-level safety checks.

Required Apple Events helper:

- P2.1 must add a dedicated Chrome Apple Events/JXA helper for browser-chrome domain commands.
- The helper must list Chrome windows and expose candidate evidence such as Apple Events window index/id when available, bounds, title, active tab index, tab id when available, active tab URL/title/loading, and candidate count.
- The helper must bind exactly one Apple Events window object to the leased OS window in the same invocation before issuing tab commands.
- Existing first-match JXA helpers are not sufficient for this contract unless they are hardened to count matches and emit uniqueness evidence.

Rules:

- All browser-chrome commands must run a same-invocation profile + window + tab preflight: verify the managed profile lease, resolve the leased OS window, raise it if needed, verify that the leased window is foreground before delivery, and capture active-tab metadata from the bound Chrome window before and after delivery when available.
- `chrome.back`, `chrome.forward`, and `chrome.reload` are intention commands. Their primary delivery path is Chrome Apple Events / JXA against the active tab of the resolved leased Chrome window.
- Apple Events must not be used as a standalone profile verifier. Chrome's scripting dictionary is window/tab-aware, but not profile-path-aware. Profile safety remains based on the CDS managed lease, Local State profile validation, AXWindow profile evidence during bootstrap, and WindowServer foreground verification.
- Apple Events delivery must bind to the leased window, not blindly use `window 1`. The implementation must derive a same-invocation Apple Events window selector from leased OS-window evidence such as window bounds, title, active-tab metadata, and frontmost verification. If that evidence cannot identify one Chrome window uniquely, the command must refuse or fall back to foreground keyboard delivery after foreground verification.
- Foreground keyboard shortcuts are allowed fallback for `back`, `forward`, and `reload` after foreground preflight. P2.1 fallback uses Chrome's browser-navigation shortcuts: `Cmd+[`, `Cmd+]`, and `Cmd+R`.
- Because current keyboard primitive support does not include `[` or `]`, P2.1 must add bracket key mapping before enabling back/forward keyboard fallback. If bracket mapping is unavailable at runtime, back/forward keyboard fallback must be reported as unavailable rather than attempted.
- `chrome.addressBarSubmit` uses foreground keyboard delivery as its primary path: raise/verify the leased Chrome window, press `Cmd+L`, type the submitted text, and press `Return`.
- `chrome.addressBarSubmit` must not default to Apple Events `set URL`, because direct URL assignment bypasses omnibox search/history/autocomplete semantics.
- AXTree may be used for observation, diagnostics, or fallback evidence, but it is not the primary target discovery path for these four P2.1 browser-chrome commands.
- Do not use AXPress, AX focus write, AX set value, CDP, Playwright, WebDriver, or `open_url` for these commands.
- Report delivery path, preflight result, Apple Events binding evidence when used, post-delivery tab metadata signals, artifacts, and known limits.

`chrome.back`, `chrome.forward`, and `chrome.reload`:

- Operate on the active tab of the Apple Events window object resolved from the leased Chrome window.
- Record before/after active-tab metadata from the same bound Apple Events window when safely available: active tab index, tab id if exposed, URL, title, and loading state.
- Treat active-tab metadata as both trace evidence and an identity check that the command operated on the selected leased window's active tab.
- Treat no history entry or unchanged URL as a semantic no-op/known limit, not automatically as action-delivery failure.
- Fallback to foreground keyboard only after the leased Chrome window is verified foreground.
- Never use Apple Events against an unbound default window as a convenience path.

`chrome.addressBarSubmit`:

- Input: `text`.
- Focuses the omnibox with foreground `Cmd+L`.
- Types the submitted text and submits with Return.
- Must not call the page `typeInput` target resolver or depend on a viewport input candidate.
- May reuse lower-level foreground keyboard/type primitives.
- Must not expose full submitted text in trace summaries beyond length or explicit command output fields.
- Must report known limits for omnibox autocomplete/history/navigation behavior.
- Must record `text_length`, delivery path, foreground preflight evidence, and before/after active-tab metadata when available. For this command, tab metadata is verification/trace evidence for the leased window's active tab; it is not the delivery mechanism.

## Safety Rules

Region filtering is not permission. The existing managed Chrome safety model remains mandatory:

- profile lease must match the managed profile.
- actions must target the resolved managed Chrome window.
- actions must verify the leased managed Chrome window is foreground before delivery.
- browser-chrome commands must bind or observe active-tab metadata from the resolved window before and after delivery when available.
- hard-stop detection still refuses dangerous states.
- clicks outside the managed window remain invalid even if a region label exists.

Apple Events are not a profile permission boundary. Browser-chrome Apple Events commands must be executed only after the CDS managed lease and foreground preflight have identified the target window, and the Apple Events window binding must be derived from that leased window.

Public `chrome.checkSafetyGate` is removed because a separate safety-check invocation can become stale before the action invocation. The safety gate remains an internal driver capability.

## Trace and QA

Trace artifacts must record region metadata:

- capture/observation artifacts include region known limits.
- OCR and AX reports include match regions.
- page action result artifacts include selected region and region source.
- observe and scroll result artifacts include scroll-boundary metrics and known limits.
- `findText` artifacts include absence semantics when no match is found in the current viewport.
- DOM raw artifacts may be recorded for trace/debug, but invoke outputs should expose normalized DOM-derived evidence rather than raw DOM payloads.
- browser-chrome action result artifacts include profile/window/tab preflight result, delivery path, Apple Events binding evidence when used, keyboard fallback evidence when used, and active-tab metadata when available.
- QA reports aggregate region-related known limits.

Visual trace reports should render region labels, scroll-boundary state, known limits for text absence, and before/after scroll progress when present, but P2.1 does not require a new inspect server.

## Tests

Required coverage:

- region-map builder classifies AX-derived page viewport.
- region-map builder emits known limits when AX structure is incomplete.
- region-map builder does not classify whole-window or cross-region ancestor nodes as `page_viewport` solely because their center lies inside `AXWebArea`.
- OCR match classification uses the capture contract and Chrome window region geometry consistently.
- AX match classification uses global logical bounds directly.
- `chrome.observe --scope viewport` returns viewport evidence only.
- `chrome.observe --scope browser_chrome` returns browser-chrome evidence only.
- `chrome.observe` returns scroll-boundary metrics when available and known limits when unavailable.
- `chrome.findText` does not match toolbar or address-bar OCR text.
- `chrome.findText found=false` reports current-viewport absence, not full-page absence.
- `chrome.findText found=false` reports that text may be below the viewport when `canScrollDown` is true or unknown.
- `chrome.waitForText` keeps OCR-only polling and uses viewport crop.
- `chrome.waitForText` attaches region metadata only on final enrichment.
- `chrome.clickTarget` does not target browser chrome.
- `chrome.typeInput` does not target the address bar.
- `chrome.typeInput` has no address-bar or browser-chrome mode.
- `chrome.scrollRegion` uses viewport-relative ratios and delivers scroll input at a viewport point without a default pre-click.
- `chrome.scrollRegion` reports before/after scroll-boundary state when available.
- `chrome.scrollRegion` reports no-progress or boundary-reached evidence when scroll metrics or visible content do not change.
- DOM-derived invoke output is viewport-clipped and does not expose raw DOM payloads as a top-level result.
- browser chrome evidence is retained in observe output with a browser region tag.
- no production source uses hardcoded browser-chrome top inset constants.
- `chrome.checkSafetyGate` is unknown through public invoke.
- driver-level `checkSafetyGate()` tests continue to pass.
- browser-chrome domain commands resolve catalog and validate inputs.
- browser-chrome domain commands perform profile + window + tab preflight in the same invocation.
- `chrome.back`, `chrome.forward`, and `chrome.reload` use Apple Events primary delivery against the active tab of the leased window.
- `chrome.back`, `chrome.forward`, and `chrome.reload` record before/after active-tab metadata from the same bound window when available.
- Apple Events delivery refuses or falls back when the Apple Events window binding is missing or ambiguous.
- keyboard fallback for `chrome.back`, `chrome.forward`, and `chrome.reload` requires leased-window foreground verification and uses `Cmd+[`, `Cmd+]`, and `Cmd+R`; tests cover bracket key mapping or explicit fallback-unavailable refusal.
- `chrome.addressBarSubmit` uses foreground `Cmd+L`, text entry, and Return as the primary path.
- `chrome.addressBarSubmit` does not call the page `typeInput` target resolver, records text length rather than full submitted text in trace summaries, and records before/after active-tab metadata when available.
- no browser-chrome domain command requires `chrome.observe` as a preceding invocation.

## Non-Goals

- No general app-region framework.
- No fixed company-search workflow.
- No reuse of page commands for browser-chrome actions.
- No `typeInput` path for address-bar submission.
- No Apple Events `set URL` default path for address-bar submission.
- No semantic `--region` option on page commands in P2.1.
- No browser close command.
- No tab switching commands.
- No fine-grained Chrome-owned UI subregion tags in P2.1; address bar, toolbar, tab strip, menu bar, and bookmarks bar tagging require a later AXTree sample-backed design.
- No hidden deletion of browser chrome evidence.
- No replacement for profile safety gates.
- No AUV compatibility claim; this is a CDS managed-Chrome enhancement.
- No cross-invoke hidden candidate state.
- No persistent driver-level or invoke-level page coverage memory.
- No `chrome-context` / `chrome-operation-context` layer in P2.1.
- No new public `OperationResult` / `InputActionResult` / `VerificationResult` contract in P2.1.
- No claim that a single viewport `findText found=false` proves full-page absence.
